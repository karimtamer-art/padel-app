Sigma is the uncertainty: high sigma means big steps, so the rating can travel fast. Who the partner and opponents are. Established gives them a correct, settled rating, so the only thing moving is your player — the clean measurement. Brand new is launch week: nobody is rated yet, every rating in the match is a guess, and the engine is learning from opponents it knows nothing about. That is the harder and more realistic case, and it is where the opponent-reliability rule does its damage.

How padel itself behaves — the rules deciding who actually wins, which no engine ever sees. The main choice is how decisive a one-level gap really is: the default assumes a level better wins about 87% of the time. Nobody knows the true figure, so if a conclusion only holds in one world, it is not a conclusion.

Is an average a fair description of a pair?

λ = 0.20

A 5.0 with a 2.0 partner and two 3.5s both average 3.5. They do not win equally often. The λ model charges a pair for being lopsided: strength = average − λ · gap.

Adjust λ to see the fit.

Boosting: does a strong partner inflate a weak player?

The same weak player plays a run of matches always with a strong partner, then the identical run with random partners. The gap between the two ratings is the inflation the partner bought.

The gap limit is an experimental match-quality control, not a proposed ranked restriction — the study found rating-gap limits do not meaningfully stop boosting. This is here to show that, not to ship it.

Is the rating about the player, or their regular partner?

One player, three phases of the same length: always with a strong partner, always with a weak partner, then random partners. A rating that identifies the individual should land in the same place all three times.

Replay real match history

no ground truth

The biggest limitation of everything else on this page is that it has to guess how decisive a level gap really is in padel. Feeding actual anonymised matches through the same engines removes the guess. Load a JSON file shaped like:

{"matches":[
  {"a":["p1","p2"], "b":["p3","p4"], "score":"6-4,3-6,7-5"},
  ...in chronological order
]}

Nobody knows a real player's true level, so error against the truth is meaningless here. What is measured instead is prediction: before each match the engine is asked who wins, and scored against what actually happened. Predictions are made before the engine sees that match, so they are genuinely out of sample.

What this page is

Every engine here is the same Dart code the batch study and the golden tests run, compiled to JavaScript. The lab cannot drift from the study because there is only one copy of the maths.

V2 is verified against production. A 244-case grid in test/ranking_lab_test.dart asserts it reproduces RatingEngine — the mirror of the SQL _settle_rating — exactly. If that ever fails, the simulator is wrong, not the assertion.

Nothing here can reach production. No Supabase client, no network call, no database. Players, ratings and matches are invented in memory and disappear when the tab closes.

True skill is hidden from the engines. They only ever see ratings, sigma, teammates, opponents and scorelines. True skill exists so you can mark the answer.
